## Что за проект

Маркетинг СИБУР Холдинга предложил кейс: страница проекта «АртНаЗавод»
(муралы на предприятиях) — long scroll **внутри** действующего sibur.ru, не
отдельный сайт. Мы не исполнитель продакшна (стек закрыт на Битрикс, приёмка
через их ИБ) — генератор лендингов делает интерактивный прототип на реальном
контенте, который заменяет отсутствующие макеты и служит агентству эталоном
поведения и структуры. Полный контекст, ограничения ТЗ и роль инструмента —
в задаче 30 на доске.

## Задача 31 — реестр объектов (сделано 2026-08-06)

`extraction/` — рабочая папка разбора презентации:

- `slides_raw.json` — сырой текст и медиа-ссылки по всем 63 слайдам, извлечено
  напрямую из XML `.pptx` (zipfile + regex по `ppt/slides/slideN.xml` и
  связанным `.rels`). Разовый шаг, воспроизводим при необходимости.
- `build_registry.py` — **группировка слайдов в объекты сделана вручную**, не
  автоматикой: прочитаны все 63 слайда целиком, определены границы объектов
  (первый слайд серии несёт заголовок+описание+год, следующие — только
  дополнительные фото без текста). Запуск: `python3 extraction/build_registry.py`
  → пишет `registry.json`, сверяет, что все referenced media-файлы физически
  есть на диске, и что все контентные слайды (4-63) покрыты хотя бы одним
  объектом.
- `build_report.py` — собирает `REGISTRY.md` из `registry.json`: реестр +
  явный раздел «Список дыр» наверху документа. Запуск: `python3
  extraction/build_report.py`.
- `previews/` — 111 медиафайлов, извлечены как есть из `.pptx` (58 МБ). Это
  **рабочие превью для прототипа, не материал для сайта** — пережаты под
  слайды. Оригиналы — в `photo.sibur.ru`, права и доступ к ним — открытый
  вопрос заказчику (задача 34).
- `registry.json` / `REGISTRY.md` — итог. **35 объектов**, 11 городов, 2022 —
  декабрь 2025 (плюс один объект без года).

**Правило, которое соблюдалось при разборе (из постановки задачи 31, повторяю
явно, чтобы не нарушить при пополнении реестра):** опечатки заказчика
(«Воронежы», «полиефинов») и незавершённые названия («?? Нейминг», `ДССК
«??»`) не исправляются молча — воспроизведены как есть с пометкой в поле
`raw_title_typo`. Считаются объекты, а не слайды: один объект может занимать
несколько слайдов (доп. фото без текста), а «Забота» на ТНХ — это один
слайд-интро и **4 отдельных объекта** внутри, у каждого свой год и описание.

**Известные дыры** (полный список с обоснованием — в шапке `REGISTRY.md`,
не пересказываю здесь второй раз):
- год не указан у 5 объектов;
- описание отсутствует у 3;
- художник не указан **практически нигде** (31 из 35) — системный пробел
  исходника, не недосмотр разбора;
- конфликт года у «Батискаф» (АГХК): слайд 56 говорит 2025, слайды 57-58 —
  2024 про тот же объект;
- координат для карты нет вообще ни у одного объекта.

Всё это — вопросы заказчику (задача 34), не додумывать самим.

## Задача 30 — замер sibur.ru (сделано 2026-08-06)

**Решение по инструменту, отличное от изначального плана.** `import-live.mjs`
из `MCP DS TOOL/tools/composition-metrics` рассчитан на отчёт
`claude-landing-pipeline/tools/visual-check` (`audit.mjs`) — тот снимает
только `viewport/pageHeight/sections/interactiveCount/cssVarsReferenced`, без
типографики, палитры и радиусов. Задаче 30 нужно больше (см. приёмку:
кегли+интерлиньяж, палитра с акцентами, радиусы, характер фонов), поэтому
написан отдельный, самостоятельный измерительный скрипт —
`measure/measure.mjs` (puppeteer, тот же приём подключения браузера, что в
`design-system-react-main/docs/product-lockup-reference/browser.mjs`: список
кандидатов путей + `PUPPETEER_CORE` явной переменной). Governance задачи это
разрешает («инструменты можно переиспользовать... но сам замер и его
результаты держать в папке пилота») — переиспользован **подход и вокабуляр**
composition-metrics (те же категории: зоны/сетка/ритм/плотность/палитра), не
буквальный код, заточенный под другой источник данных.

**Запуск:** `cd measure && node measure.mjs` → `raw/<page>-<viewport>.json` +
`screenshots/`. Три страницы (главная, листинг решений, детальная история
клиента — она ближе всего по духу к будущей странице муралов), три
брейкпоинта (1440/834/390), скролл до конца перед снятием (часть блоков
рендерится лениво).

**Главный результат — таблица сравнения с DS в `measure/REPORT.md`.**
Коротко, самое важное:
- **Гипотеза «шкала DS слишком мала» не подтвердилась.** Сайт нигде не
  поднимается выше H1=56px — это практически совпадает с
  `--font-size-h1: 54px`. Расширять шкалу не нужно.
- **Настоящий разрыв — не в размере, а в трекинге.** DS даёт положительный
  letter-spacing (0.3px, «интерфейсный» набор), сайт — отрицательный
  (−0.84…−1.12px, плотный «редакционный»). Это надо решать отдельным
  токеном трекинга для дисплейных заголовков, не новым размером.
- **Тёплый акцент существует и подтверждён на трёх страницах**: `--red:
  #fd5a42`, применяется через класс `.red` на `<span>` внутри заголовков для
  смыслового выделения слова. В DS нет ничего на роль «акцент бренда» —
  только `--color-chart-orange` (для графиков) и `--color-status-warning`,
  использовать их для акцента в тексте нельзя, семантика не та.
- **Бренд-цвет сайта и DS не идентичны**: `--sibur-dna: #02818a` (сайт) vs
  `--color-background-brand: #008c95` (DS) — оба тил, разные значения.
  Решение, какой брать за основу маркетинговой темы, — задача 32.
- **Бенто-сетка подтверждена вживую, не по референсу пользователя**: на
  главной — 4 неравные плитки в ряд, на листинге — карточки с фото и
  градиентной подложкой снизу; на мобильном (390px) весь бенто схлопывается
  в одну колонку, сохраняя скруглённость и структуру карточек.
- Пилюльные радиусы кнопок (50px/100px) — DS-шкала кончается на 30px; это не
  повод расширять шкалу числом, а повод завести флаг «пилюля» отдельно.

**Честно отмеченное ограничение**, не скрыто в отчёте: высота шапки колеблется
67–93px между измерениями — вероятно, гонка между скроллом-до-конца (лениво
рендерится часть блоков) и возвратом наверх перед снятием размеров. Число не
финальное, для точного значения мерить нужно без предварительного скролла.
Слой `--redesign-*`/`--emerald`/`--terracotta`, объявленный в CSS сайта, на
трёх измеренных страницах не проявился — возможно, живёт на страницах вне
выборки; если появится доступ к Figma (задача 34), сверить там надёжнее, чем
обходить весь сайт вручную.

## Задача 33 — прототип + пакет передачи (сделано 2026-08-06)

`prototype/` — отдельное, **не git-трекнутое** Vite+React+TS приложение
(осознанно вне `MCP DS TOOL`/`claude-landing-pipeline`, чтобы данные
заказчика из задачи 31 не попали в GitHub-репозиторий дизайн-системы). Тот же
`file:`-паттерн подключения `@sibur/design-system-react`/`@sibur/
design-tokens`, что в `klik-atom`, с поправкой на глубину пути.

7 секций ИА в порядке ТЗ (первый экран → о проекте → показатели → история по
годам → карта → плитка объектов → процесс создания), все цифры и тексты — из
`extraction/registry.json`, честные плейсхолдеры только там, где у заказчика
реально нет данных (фото объектов, координаты для карты).

**Timeline не использован сознательно** — его семантика (линейный прогресс:
пройдено/сейчас/будет) не подходит просматриваемому архиву, где все года
одинаково «завершены». История собрана из `Stack`/`Typography` с
горизонтальным `overflow-x` на собственном контейнере — не блокирует
вертикальный скролл страницы.

**Обе ключевые механики проверены puppeteer, не только «должны работать»:**
Inline Expansion (`grid-column: 1/-1` на раскрытой карточке) — клик
разворачивает карточку в потоке; Deep Link (`location.hash` +
`history.replaceState`) — прямой переход по `#slug` сразу раскрывает нужный
объект без перезагрузки.

**Гейт композиции** (`tools/visual-check`, профиль `embedded_gallery`,
`--set minSectionGap=40 --set minSectionPadding=40`) — зелёный на 1440×900 и
390×844, отчёт в `prototype/evidence/visual-check/`. По пути найдены и
исправлены собственными силами (не сообщены пользователем) три реальных
дефекта — полное описание в задаче 33 доски `tasks.md`, коротко: (1) 4- и
3-колоночные Grid для показателей не адаптировались на мобильном — текст
наезжал и обрезался, добавлены брейкпоинты; (2) `server.fs.allow` в
`vite.config.ts` был `['..']`, реально нужно `['../..']` — пакеты ДС лежат в
соседней папке уровнем выше, не в предке проекта; (3) три CSS-переменные в
инлайн-стилях (`--color-border-light` и т.п.) оказались несуществующими —
не сверил через MCP `get_tokens` до использования, поймано гейтом
(`css_vars_unresolved`), не пользователем.

Пакет передачи агентству — `../HANDOFF-agency.md` (на уровень выше, рядом с
этим файлом): как запустить, структура секций, техническое описание обеих
механик в терминах, переносимых на любой стек, явный список открытых
вопросов заказчику. Формат передачи и контакты (Андрей Дедов) — ждут задачу
34, пункт 4.

## Сессия 2026-08-14 — первый экран: видео вместо фото-заглушки

Пользователь передал 3 реальных видео заказчика (`content/`, вне git) и
попросил заменить фото-заглушку «Батискафа» на первом экране видеорядом с
переключением между роликами, звук выключен по умолчанию, высота как у
прежнего баннера. Это было прямо предусмотрено в комментарии кода
(`gallery-theme.scss`, ныне убран): «Когда фото заменят на видеоряд
(обещано позже)...» — то есть не новая идея, а реализация того, что уже
планировалось.

**Файлы:** `content/*.mp4`/`*.mov` (3 шт, ~958 МБ суммарно, без сжатия —
`ffmpeg`/`brew` на машине не оказалось) скопированы в
`prototype/public/hero/` под ASCII-именами (кириллица и `#` в исходных
именах непригодны для URL): `tnh-shishka.mp4` (граффити на резервуаре,
Томскнефтехим — совпадает с объектом `tnh-zabota-rezervuary`),
`sosedi-sibura.mp4`, `sibur-color.mov`.

**`.mov` реально проигрывается в Chromium** (проверено headless-браузером
перед тем, как встраивать: `readyState: 4`, `videoWidth: 1920`, без
ошибок) — H.264 внутри QuickTime-контейнера, а не ProRes/другой кодек, с
которым были бы проблемы вне Safari.

**Один `<video>` в DOM за раз, не три слоем друг на друге.** Исходники по
250-450 МБ каждый — одновременный рендер трёх `<video src=...>` заставил
бы браузер начать буферизовать все сразу. `key={src}` на элементе
форсирует React пересоздать `<video>` при смене индекса, а не мутировать
`src` у существующего (тот же приём, что уже был у `onLoadedMetadata` в
`ObjectCard.tsx` для центровки карусели — здесь проще, повторного расчёта
позиции не нужно).

**Компоновка:** `.gallery-hero__media` (контейнер) → `.gallery-hero__video`
(сам `<video>`, `object-fit: cover`, `position: absolute; inset: 0` — то
же поведение full-bleed, что раньше давал `background: url() center/cover`
у фото) → `.gallery-hero__scrim` (без изменений) → `.gallery-hero__nav`
(prev/next, `IconButton variant="overlay"`, тот же паттерн, что уже
использует `.gallery-card__media-nav` в карусели объекта, только на всю
высоту героя). `min-height: 520px` секции не менялся — высота сохранена
как есть, ровно требование пользователя.

**Не сделано (сознательно, не спрашивалось):** пережатие видео под
web-битрейт (для реального продакшн-сайта понадобится, для локального
стенда на loopback — не проблема, размер файла не влияет на время
загрузки), привязка конкретного видео к конкретному объекту галереи ниже
по странице (видео на первом экране не связаны с конкретной раскрытой
карточкой).

Проверено: `tsc -b` чисто, визуально на живом стенде (`localhost:5175`)
все три видео переключаются, звук выключен на каждом (`muted: true` в
DOM), 1440px и 390px без горизонтального переполнения (`scrollWidth ===
clientWidth`).

**Поправка тем же днём: автопереход между роликами добавлен.** По
просьбе пользователя — `onEnded` на `<video>` переключает на следующий
ролик (без `loop`, иначе `onEnded` не наступил бы), после последнего
снова первый. Стрелки остаются как ручное переключение, не заменяются.

## Сессия 2026-08-14 (вторая) — деплой на тестовый ВПС, два бага после него

Развёрнули прототип на тестовом ВПС Only (доступ и история деплоя — в
памяти `reference_artnazavod_only_vps_ssh_key`/`project_artnazavod_pilot`,
здесь не дублирую). После деплоя пользователь на живом сервере нашёл два
дефекта в `ObjectCard.tsx` — карусели фото/видео объекта.

**1. Демо-видео (`public/media/demo-video-1.mp4`/`-2.mp4`) отдавали
403 на сервере.** Причина — права `600` на самих файлах локально (когда и
почему появились именно такие права, не выясняли), `rsync -az`
(archive-режим) честно перенёс их как есть на сервер, где nginx работает
не от того же юзера. Фикс — `chmod 644` и локально, и на уже залитых
файлах сервера. Симптом был виден только на двух конкретных файлах, не на
всех медиа (видео первого экрана и фото объектов грузились нормально) —
это и подсказало, что дело в правах одного места, а не в деплое целиком.

**2. Клавиатурного листания карусели не было вообще — не регресс, а
отсутствовавшая функция.** В `ObjectCard.tsx` не было ни одного
обработчика `onKeyDown`/`Arrow*` до этой сессии (проверено `grep` по
всему `src/`) — только клик по кнопкам-стрелкам и превью. Добавлен
`handleGalleryKeyDown` на обёртке `.gallery-card__expanded-media-wrap`
(не на сам скроллящийся `.carousel` — так стрелки работают одинаково,
где бы фокус ни стоял внутри). Второй нюанс: при раскрытии карточки
React заменяет `<button>` (свёрнутое состояние) на `<div>` (раскрытое) —
старый DOM-узел с фокусом исчезает, браузер сбрасывает фокус на `<body>`,
и стрелки сразу после раскрытия никуда бы не попадали. Обёртка получила
`tabIndex={-1}` (программно фокусируемая, но не в общей Tab-последовательности)
и явный `.focus({ preventScroll: true })` в том же эффекте, что уже делает
`scrollIntoView` при переходе `false → true`.

Проверено: `tsc -b` чисто (тестов в этом проекте нет — их гоняет только
`design-system-react-main`), Playwright headless — индекс активного
слайда меняется `0→1→2→1` по `ArrowRight`/`ArrowLeft`, то же самое
воспроизведено уже на самом ВПС после передеплоя. Оба видео отдают 200
и локально, и на сервере.

**Поправка тем же днём: фикс клавиатуры сам породил визуальный баг —
синие полоски сверху и снизу карусели.** Программный `.focus()` на
`.gallery-card__expanded-media-wrap` заставил браузер рисовать дефолтный
`outline` фокуса вокруг всего full-bleed блока (`width: 100vw`) — левый и
правый края outline уходят за пределы вьюпорта, остаются видны только
горизонтальные линии сверху/снизу через весь экран. Пользователь поймал
на скриншоте сразу после первого фикса. Решение — `outline: none` на
`&:focus-visible` именно этой обёртки: она получает фокус только
программно ради перехвата стрелок, не участвует в обычной Tab-навигации
(`tabIndex={-1}`) и не является видимым элементом управления сама по
себе — настоящие кнопки/превью внутри сохраняют свой собственный
`focus-visible`. Проверено: `getComputedStyle(...).outlineStyle === 'none'`
headless-браузером, визуально на скриншоте линий нет, клавиатурная
навигация по-прежнему работает. Передеплоено на ВПС.

**Проблема объёма медиа решена сжатием, не только архитектурой.** Сырые
файлы заказчика — дампы с камер/дронов, до 423 МБ штука, 3 ГБ суммарно;
`ffmpeg`/`imagemagick`/`brew` на машине не было. Решение — npm-пакеты, не
системные установки: `sharp` (фото, resize ≤1600px + mozjpeg q80) и
`ffmpeg-static` (видео, ≤1080p, H.264 CRF 26, AAC) в
`prototype/scripts/prepare-final-media.mjs`. Результат:
фото 1 ГБ → 54 МБ, видео объектов 2 ГБ → 428 МБ, хиро 958 МБ → 33 МБ.
Грабля по пути: `libx264` падает на нечётной ширине/высоте после ресайза
вертикального видео (807×1080) — нужен второй `scale=trunc(iw/2)*2:
trunc(ih/2)*2` в цепочке фильтров, иначе `ffmpeg` завершается с ошибкой
`width not divisible by 2`.

**Хиро-нарезка первого экрана заменена полностью** — 6 роликов из
`___НАРЕЗКА для шапки` (не 3, как раньше), тот же паттерн переключения
(`onEnded`, один `<video>` в DOM за раз), просто новый список путей в
`HeroSection.tsx`.

**Пакет передачи (`dist-singlefile/`) сменил форму.** Раньше — ровно один
HTML-файл с base64-инлайном всего. С объёмом видео финальной фактуры
(сотни МБ даже сжатых) base64 в одном файле стал нежизнеспособен —
браузеры плохо тянут гигантские data:-URI video, а +33% к размеру от
base64 добивает контрольную. Решение: `build-singlefile.mjs` по-прежнему
инлайнит фото/JS/CSS/шрифты (маленькие после сжатия), но видео (`/media/`,
`/hero/`) больше не инлайнится — вместо этого пути в JS-бандле становятся
относительными (`media/...`, `hero/...`), а сами папки копируются рядом с
`index.html`. Итог — не файл, а маленькая папка
(`dist-singlefile/АртНаЗавод-прототип/`, ~516 МБ: 76 МБ HTML + ~440 МБ
media/hero), которую так же просто зазипить и отправить коллеге. Проверено

## Сессия 2026-08-21 — техническая готовность к публикации

Пользователь спросил прямо: «код полностью готов технически для
публикации на бою?». Аудит по коду (не на глаз) нашёл реальный блокер и
несколько пробелов; по прямому запросу пользователя («лечим всё, чтобы
при публикации спешно не устранять») всё, что можно было починить
технически, — починено и проверено.

**Главный блокер — абсолютные пути от корня домена.** На встрече 14.08
было прямое условие: раздел встраивается не в корень sibur.ru, а в
поддиректорию за прокси, все ссылки должны быть относительными. До этой
сессии условие не выполнялось нигде: `vite.config.ts` не задавал `base`
(Vite по умолчанию даёт `/assets/...`), а `HeroSection.tsx`/`AboutSection.
tsx`/генератор `objects.ts` хардкодили `/hero/...`, `/logo/...`,
`/photos/...`, `/media/...`.

Фикс: `vite.config.ts` → `base: './'` (стандартный Vite-паттерн для
встраивания в неизвестную поддиректорию — переписывает JS/CSS/шрифты/
`url()`, которые проходят через сборку). Ручные рантайм-строки (Vite их
не видит) — убран ведущий `/` в `build-objects-ts.mjs` (генератор
`photos`/`media`), `HeroSection.tsx` (`HERO_VIDEOS`), `AboutSection.tsx`
(лого). `build-singlefile.mjs` тоже был завязан на ведущий `/` в двух
местах (regex поиска тега `<script src="/assets/...">` и построение
`urlRef` для инлайна фото/лого) — переписан под новый формат (шрифты
теперь ссылаются просто именем файла из той же папки, `./SbrIcons-....
woff2`, а не `/assets/SbrIcons-...`).

**Впервые за всё время проекта реально проверено требование с 14.08**, не
на словах: `dist/` скопирован в `/tmp/nested-test/art-na-zavod/`,
статика поднята `python3 -m http.server` в родительской папке, зашёл на
`http://localhost:4400/art-na-zavod/` (с завершающим слэшем — без него
`http.server` сам отдаёт 301, так же обычно ведёт себя корректно
настроенный nginx `location`) — headless puppeteer: 32 карточки, все
медиа грузятся, deep-link, клавиатура, хиро-видео декодируется, 0 ошибок
консоли, 0 неудачных запросов. То же самое перепроверено и в корне (порт
preview) — регресса от смены `base` нет.

**Оговорка, которую не могу проверить сам**: относительные пути работают
только если прокси отдаёт URL раздела с завершающим слэшем
(`sibur.ru/art-na-zavod/`, не `sibur.ru/art-na-zavod`) — стандартная
настройка `location` в nginx, но её делают другие сотрудники SIBUR, не
пользователь и не я. Это единственное условие публикации, которое
осталось вне моего контроля.

**SEO/метаданные.** `index.html` — `<title>` был буквально «АртНаЗавод —
прототип» (утекло бы на боевой сайт как есть), заменён на реальный
заголовок заказчика (тот же текст, что уже одобрен и стоит в «О
проекте» — не выдумка). Добавлены `meta description`, `og:title`,
`og:description`, `og:type` (тем же текстом — новую рекламную копию не
придумывал), и `<link rel="icon">` на существующий `logo/artnazavod-logo.
svg` — закрыл настоящую 404 favicon.ico, которая была в консоли с самого
начала работы над прототипом.

**Code-splitting карты.** `MapSection` (Leaflet + маркер-кластеризация)
тянул на карту вне зависимости от того, долистал ли посетитель до неё —
единый JS-чанк был ~528 КБ (gzip ~153 КБ), Vite уже предупреждал
(`chunks are larger than 500 kB`). Обёрнут в `React.lazy`/`Suspense` в
`App.tsx` (`fallback={null}` — карта ниже первого экрана, мигать нечему).
Результат: основной чанк — 337 КБ (gzip 94 КБ), Leaflet уехал в отдельный
чанк 193 КБ (gzip 59 КБ), подгружается только при скролле к карте.
Warning про >500 КБ пропал. Проверено headless — карта после скролла
рендерится, 10 маркеров/кластеров на месте, ошибок нет.

**Побочная находка: `React.lazy` несовместим с инлайн-пакетом
`dist-singlefile/` — не багфиксом, а архитектурным ограничением.** Первая
попытка почина́ки — скопировать чанк карты (`MapSection-*.js/css`) рядом с
`index.html` в `build-singlefile.mjs` — сначала упёрлась в CORS браузера на
динамический `import()` с `origin: null` (это и есть `file://`, не чинится
копированием файлов). Попытка обойти через локальный сервер вскрыла кое-что
хуже: `MapSection-*.js` импортирует общие биндинги (React/DS) ИЗ главного
JS-чанка по его файловому имени, а этот чанк уже заинлайнен в сам HTML —
копирование его же как отдельного файла для чанка карты создаёт ВТОРОЙ,
независимый экземпляр модуля (ES-модули дедуплицируются по URL, у инлайн
`<script>` своего URL нет), который пытается сам примонтировать React
поверх первого — `React error #321`, `removeChild` на чужом узле, все
фото 404 (второй инстанс тянет их не-инлайненными путями). Правильное
решение — не пытаться обойти это, а **изолировать сбой**: секция карты
обёрнута в `ErrorBoundary` (новый `src/components/ErrorBoundary.tsx`,
class-компонент — хуков-эквивалента React не даёт), `build-singlefile.mjs`
больше не пытается тащить чанк карты вообще. Итог: в `dist-singlefile/`
карта просто отсутствует (изолированно, без крэша остального — карточки,
фото, хиро-видео работают и через `file://`, и через любой сервер), а на
живом сайте (всегда http/https, чанк грузится нормальным сетевым запросом)
код-сплиттинг работает без всяких оговорок. `ErrorBoundary` заодно закрывает
и реальный прод-риск: без неё сетевой сбой у настоящего посетителя при
загрузке чанка карты уронил бы всё приложение целиком, не только карту.

**Найдено и осознанно НЕ починено:**
- В `dist/` лежит неиспользуемый `pdf.worker.min-....mjs` (~1 МБ) —
  тянется транзитивно через `react-pdf` внутри самого пакета
  `@sibur/design-system-react` (какой-то PDF-компонент DS, на этой
  странице не используется вообще). Подтверждено grep'ом по
  `dist/index.html` и главному бандлу — ссылок на файл нет, браузер его
  не запрашивает, реальной цены в рантайме нет. Починить можно было бы,
  только патчить сам пакет ДС (отдельный управляемый репозиторий, рискованно
  перед публикацией), либо хрупкий хак в `vite.config.ts` — решил не
  трогать, стоит завести как gap дизайн-системы отдельно.
- `package.json` держит `@sibur/design-system-react`/`@sibur/
  design-tokens` через `file:`-ссылки на `../../ux-rules-mcp/...` —
  собрать проект можно только на этой машине. Деплой это не блокирует
  (`deploy.sh` всегда собирает локально и льёт только `dist/`), но явно
  задокументировано прямо в `deploy.sh` (шапка скрипта) — никогда не
  `git clone` + `npm install` на боевом сервере.

**Осознанно не тронуто по решению пользователя** (спросил явно через
`AskUserQuestion`, оставить как есть): плейсхолдер-черновик в тексте
карточки «Обереги Югры» («[текст объединённой карточки — черновик...
автор обновит]») и плитка статистики «ХХ тыс. м² искусства» — оба
дождутся реальных данных от заказчика, трогать не стал.

**Не в моей власти, требует данных/действий заказчика или других
сотрудников SIBUR** (перечислено пользователю отдельно, не код-задачи):

## Сессия 2026-08-21 (третья) — спутниковые тайлы вместо схематичных карт

Заказчик поднял чувствительный вопрос: на схематичных картах (OSM,
CARTO — проверил оба вживую) на низком зуме видна административная
граница по линии ДНР/ЛНР/Запорожской/Херсонской областей — компания
боится политических последствий вне зависимости от того, в чью пользу
её нарисовать. Явное решение пользователя: не занимать никакую позицию
(«компания не обязана поддерживать позицию государства»), убрать
административные границы регионов с карты вообще, оставить только
город-маркеры на нейтральной подложке.

**Решение — спутниковые тайлы (Esri World Imagery) вместо схематичных.**
Не «более нейтральная» схема, а структурно другой тип данных: аэрофото
физически не содержит политических границ ни в чьей трактовке — это не
редакционный выбор карты, а природа спутникового снимка. Проверено
напрямую (скачаны и визуально сверены тайлы CARTO Positron, в т.ч.
`light_nolabels`, и Esri World Imagery над Крымом/Донбассом на
z5-z6) — у CARTO граница видна в обоих вариантах (снятие подписей не
снимает саму линию), у Esri линий нет вообще ни на одном уровне зума.

`MapSection.tsx`: `L.tileLayer` переключён на `server.arcgisonline.com/
.../World_Imagery/...` (Esri, бесплатно, без API-ключа — тот же принцип
доступности, что был у OSM; порядок сегментов URL другой — `z/y/x`, не
`z/x/y`). Монохромность (требование ТЗ) не пострадала — тот же CSS-фильтр
`grayscale(1) contrast(1.05)` в `gallery-theme.scss`, который раньше
обесцвечивал схематичные тайлы, точно так же работает и на спутниковом
снимке, правки CSS не понадобилось.

Проверено headless: клик по маркеру/попап работают, клавиатура/deep-link/
карточки не задеты, ошибок и неудачных запросов нет. Передеплоено на
dribble.

## Сессия 2026-08-21 (четвёртая) — брендовые метки, зум тачпадом, полировка

Четыре мелких правки карты за один заход.

**Метки — брендовый цвет.** Дефолтный PNG-маркер Leaflet (всегда синий,
перекрасить нельзя без замены файла) заменён на `L.divIcon` с
инлайн-SVG-каплей: `fill="var(--color-background-brand)"` — тот же
токен, что уже красит другие акценты на странице, не хардкод хекса.
Попутно вскрылась и почищена ловушка: `filter: grayscale(1)` раньше
висел на всём `.gallery-map__leaflet` (контейнере карты целиком) — раз
маркеры рендерятся ВНУТРИ этого же контейнера, тот же фильтр гасил бы и
их цвет тоже (`filter` родителя применяется к уже скомпонованному виду
всего поддерева, ребёнок не может «отменить» обесцвечивание для себя
одного). Перенёс фильтр конкретно на `.leaflet-tile-pane` — тайлы
остаются монохромными (ТЗ), метки полноцветные.

**Зум тачпадом (жалоба пользователя: pinch на MacBook зумит сайт, не
карту).** `scrollWheelZoom: false` был выставлен намеренно раньше —
простой скролл над картой должен листать страницу, не зумить карту
(иначе страницу под картой нельзя проскроллить мышью). Но у этого же
флага побочный эффект: Leaflet вообще не слушает `wheel`-события, а
жест pinch-to-zoom на трекпаде Mac браузер доставляет именно как `wheel`
с `ctrlKey: true` (трекпад MacBook — не тачскрin, отдельного touch-жеста
нет, только эмуляция через клавишу-модификатор) — событие улетало
напрямую в браузер и зумило страницу целиком. Решение — свой
`wheel`-обработчик на контейнере карты: событие БЕЗ `ctrlKey` не трогаем
(страница листается как раньше), событие С `ctrlKey` (реальный pinch
ИЛИ явный Ctrl+скролл мышью) — `preventDefault()` + `map.setZoom(...)`
вручную. `zoomSnap: 0.25`/`zoomDelta: 0.5` — плавный дробный зум вместо
скачков по целым уровням, иначе pinch ощущался бы рывками. Проверено
headless (реальный трекпад не эмулируется точно, но механизм
verified): обычный wheel над картой двигает `window.scrollY` (скроллит
страницу), `wheel` с `ctrlKey:true` — `window.scrollY` не меняется
(браузер не зумит страницу), а тайлы карты грузятся с бОльшим номером
zoom в URL (карта реально приблизилась).

**Подпись про город/точный адрес объекта убрана** («Метка показывает
город, не точный адрес объекта…») — по просьбе пользователя, без замены.

**Атрибуция Esri уменьшена, не удалена.** Пользователь прислал скриншот
с просьбой скрыть плашку атрибуции — полностью убрать её нельзя: это
условие бесплатного использования тайлов Esri (то же самое, что раньше
требовал OSM) — сообщил пользователю прямо. Компромисс — `font-size:
10px`, полупрозрачный фон, вместо жирной белой плашки по умолчанию у
Leaflet: формально на месте, визуально почти незаметна.

Передеплоено на dribble.

**В тот же день пользователь отменил монохромность карты вообще**
(«попробуй саму карту сделать оригинального цвета — как снимок со

**Схема ровно та, что отрабатывали на тестовом ВПС:** сборка локально,
`rsync -az --delete` каталога `dist/` (491 МБ уехали за 19 секунд, ~27 МБ/с),

## Сессия 2026-09-04 (пятая) — кэш браузера отдавал снятый ролик

Пользователь сообщил, что на боевом стенде в шапке играет не тот ролик, и
что набор должен совпадать с `prototype/public/hero`. Сверка показала, что
на сервере всё правильно: MD5 всех четырёх файлов совпадают с локальной
папкой побайтово, и `curl` скачивает именно новые файлы.

**Причина — кэш браузера, а не деплой.** Медиа отдавались с `expires 7d`,
а имена файлов у нас стабильные (`hero-1.mp4`, `photos/<slug>/01.jpg`) —
меняется содержимое под тем же именем. Браузер, однажды загрузивший
старый `hero-3.mp4` (снятый ролик, 12 МБ), продолжал играть его из кэша и
даже не спрашивал сервер — до 11 сентября.

**Что изменено:** для фото, видео и шрифтов вместо `expires 7d` теперь
`Cache-Control: no-cache`. Это не «не кэшировать», а «кэшировать, но
каждый раз переспрашивать»: браузер шлёт `If-None-Match`, сервер отвечает
пустым 304 (проверено), а при подмене файла отдаёт новый. Хешированные
файлы сборки в `/assets/` остаются `immutable` — там имя меняется вместе
с содержимым, и переспрашивать незачем.

**Конфиг nginx переехал в репозиторий** — `prototype/deploy/nginx-
artnazavod.conf`, `deploy-prod.sh` заливает его при каждом деплое. До
этого он жил только на самой машине: воспроизвести настройку по
репозиторию было невозможно, а портальной команде это понадобится при
подключении проксирования.

**Оговорка, которую нельзя обойти с нашей стороны:** у уже закэшированной
копии свой срок жизни, записанный в момент старой загрузки. Новый
заголовок она увидит только при первом обращении к сети, поэтому один раз
нужен жёсткий перезагруз страницы (Cmd+Shift+R). Дальше подмена файлов
подхватывается сама.

Побочно замечено и исправлено: `expires` + `add_header Cache-Control`
давали в ответе два заголовка `Cache-Control` одновременно
(`max-age=604800` и `public` отдельными строками).

## Сессия 2026-09-11 — фавикон, mixed content на sibur.ru, noindex под прокси

**Фавикон заказчика.** Сначала пришёл `Fav.png` 120×120, затем — новая
версия в `FAV_АртНаЗавод.eps` (Illustrator 30.8, BoundingBox 140×140).
Раньше `<link rel="icon">` указывал на `logo/artnazavod-logo.svg`; теперь
в `public/` лежат три файла — `favicon-32.png`, `favicon.png` (256),
`apple-touch-icon.png` (180), все прописаны в `index.html`
относительными путями (условие проксирования).

**Как из EPS получен растр — без Ghostscript, это стоит записи.** На
машине нет ни `gs`, ни ImageMagick, ни Inkscape, а brew не ставится;
`sips` и `qlmanage` EPS не берут (поддержка PostScript в macOS давно
опирается на внешний Ghostscript, которого нет), pyobjc/Quartz в системном
python3 отсутствует. Встроенного PDF-потока в файле тоже не оказалось
(`%PDF-` не встречается — это чистый PostScript, не AI-EPS с PDF-совместимостью).
Рабочий путь нашёлся в XMP-метаданных Illustrator: `xmpGImg:image` — это
base64 превью 256×256 JPEG, его достаточно для набора иконок.
**Грабля:** внутри XMP переносы строк закодированы как `&#xA;`, и если
чистить base64 только от пробелов, символы энтити попадают в поток —
JPEG декодируется частично (заголовок валидный, дальше мусор, `sips`
молча не читает файл). Убирать `&#xA;`/`&#x9;` явно до `b64decode`.
Если понадобится честный векторный рендер — просить у заказчика SVG/PNG
или ставить Ghostscript, thumbnail'а хватает только для иконок.

**Коллега подключил раздел через `<object>`, страница была пустой.**
На `https://www.sibur.ru/ru/artnazavod/` стояло
`<object data="http://artnazavod.sibur.ru/">` — active mixed content:
HTTPS-страница тянет HTTP-ресурс, браузеры такое блокируют жёстко и молча.
Проверено с обеих сторон: DNS `artnazavod.sibur.ru` → 194.58.118.240,
по HTTP 200, по HTTPS соединение не устанавливается (443 открыт, TLS
никто не слушает); в отданном HTML sibur.ru действительно `<object>`.
Фрейминг наш сервер не запрещает — ни `X-Frame-Options`, ни
`frame-ancestors` не выставлены. Решение по развилке (подтверждено
пользователем): **остаёмся на проксировании**, iframe/object не нужен —
тогда TLS терминируется на стороне sibur.ru и mixed content отпадает сам.

**`noindex` переписан под проксирование.** Прежнее правило ловило только
голый IP; после появления имени `artnazavod.sibur.ru` origin стал открыт
роботам и в выдаче завёлся бы дубль будущей страницы sibur.ru. По `$host`
прокси от прямого запроса не отличить — nginx при `proxy_pass`
подставляет Host апстрима. Поэтому `map` теперь по `$http_x_forwarded_host`:
по умолчанию `noindex, nofollow`, пусто — только для `www.sibur.ru`/`sibur.ru`.
Умолчание выбрано в сторону noindex сознательно: не пробросили заголовок —
теряем индексацию (заметно, лечится строкой), а не плодим дубль.
**После подключения прокси проверить:**
`curl -sI https://www.sibur.ru/ru/artnazavod/ | grep -i robots` — пусто.
Требования к прокси, переданные коллеге: слэш в конце URL раздела
(редирект 301 без него), `proxy_set_header X-Forwarded-Host $host`,
`proxy_http_version 1.1` и никакого усечения Range — видео шапки
раздаётся range-запросами.

Развёрнуто на боевой ВПС (`deploy-prod.sh`) и на стенд dribble
(`deploy.sh`), иконки сверены по sha256 с локальными на обоих.

### GitHub оживлён как зеркало без медиа (11.09)

`main = 4bd3464` с 21.08. Пользователь попросил его оживить; `origin`

Развилка была в медиа: с 04.09 в репозитории лежат 251 фото (~47 МБ

Линия GitLab после переезда имеет другой корень, поэтому история не
склеивалась напрямую. Рецепт (воспроизводить при следующем зеркалировании):

```bash
git replace --graft <первый коммит после переезда> 4bd3464   # старый tip GitHub
git branch -f github-main <текущая верхушка>
FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch -f --prune-empty \
  --index-filter 'git rm -r --cached -q --ignore-unmatch \
     prototype/public/photos prototype/public/media prototype/public/hero' \
  -- 4bd3464..github-main
git push github github-main:main        # fast-forward, без --force
git replace -d <sha>                    # графт снять, рабочую линию не трогать
git for-each-ref --format='%(refname)' refs/original/ | xargs -n1 git update-ref -d
```

Результат: `main = fff9da9`, 23 коммита, история продолжает старую
(fast-forward, ничего не затёрто), `prototype/public/` содержит только
иконки и `logo/`, LFS-объектов в ветке нет — квота GitHub не тратится.
Коммиту про медиа переписано сообщение, чтобы не обещать файлов, которых
в этой линии нет. `prototype/evidence/` остаётся — он был на GitHub и
раньше.

Пуш — Basic auth через `http.extraHeader` (см. память
`reference_git_push_auth_workaround`), токен временный, в `.git/config`
не попадает.
