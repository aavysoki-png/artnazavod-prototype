# План: автоматическое обновление контента с Я.Диска

Составлен 2026-09-11. Решения заказчика работ (пользователя) зафиксированы:
канал загрузки — **Яндекс.Диск**, **предпросмотр обязателен**, видео —
**ночным прогоном**, срочное видео — руками через пользователя.

Цель: коллега кладёт фотографии в папку на Диске и больше ничего не делает.
Фото появляются на предпросмотре в течение ~10 минут, на боевом — после
явной команды человека.

---

## 1. Контракт папки на Диске

Один раз объясняется коллеге, дальше не меняется:

```
АртНаЗавод/                       ← публичная ссылка на эту папку
  Объекты/
    ЗСНХ_Добрые соседи СИБУРа/    ← имя папки закреплено за объектом
      01 обложка.jpg              ← порядок задают цифры в начале имени
      02 общий план.jpg
      _не для сайта/              ← папки с «_» робот не открывает
  Шапка/
    hero-1.mp4
```

Правила, которые робот соблюдает и о нарушениях сообщает, а не угадывает:

- **папка = объект.** Соответствие «имя папки → slug» лежит в `folders.json`
  (в репозитории, копируется на сервер). Незнакомая папка — робот её
  пропускает и пишет в отчёт: «папка X новая, скажите slug»;
- **порядок — по имени файла** (`localeCompare 'ru'`), первый файл становится
  обложкой. Коллеге достаточно нумеровать префиксом;
- **мусор отсеивается**: не-медийные расширения, `Screenshot*`, `noroot*`,
  `gemini*`, `photo_<дата>*`, скрытые файлы, вложенные папки. Всё отсеянное
  перечисляется в отчёте поимённо — молчаливого `[skip]`, как сейчас, быть
  не должно;
- **тексты, годы, площади** роботом не трогаются: они приходят из
  xlsx-каталога через существующую цепочку `build-manifest-from-catalog.mjs`.
  Заведение нового объекта и привязка папки — ручная операция раз в квартал.

Открытый вопрос: публичная ссылка рабочей папки. Для поставки использовалась
`disk.yandex.ru/d/12tsuaJPbYuOeQ` — нужна либо она же, либо новая постоянная.

## 2. Что меняется в коде прототипа

Каждый пункт полезен сам по себе, независимо от робота.

1. **Контент из сборки в рантайм.** Сейчас `scripts/build-objects-ts.mjs`
   генерирует `src/data/objects.ts`, который импортируют `HistorySection`,
   `MapSection`, `ObjectsSection`, `ObjectCard` — то есть любое новое фото
   требует `npm run build` и rsync всей `dist/`. Заменяется на `content.json`,
   который страница запрашивает относительным путём (`base: './'` не ломается,
   условие встраивания в поддиректорию сохраняется). После этого обновление
   контента не требует ни Node, ни сборки.
2. **Шапка — из листинга,** а не из массива `HERO_VIDEOS`
   (`HeroSection.tsx:18-24`). Сейчас добавленный ролик сайт не видит.
3. **Имена файлов с хешем содержимого** (`01.a1b2c3.jpg`) вместо стабильных
   `01.jpg`. Снимает граблю с кэшем (сейчас после обновления нужен
   Cmd+Shift+R) и позволяет отдавать медиа `immutable` вместо `no-cache`.
4. **Ветка полной очистки в `prepare-final-media.mjs` в роботе не
   используется.** `ensureEmptyDir(photosOut)` однажды уже стёр всё
   подготовленное медиа (журнал, сессия 04.09) — в автоматическом цикле
   такой ветки быть не должно вообще.

## 3. Робот на боевом ВПС

Сервер: Debian 13, 4 ядра, 8 ГБ, 27 ГБ свободно. **Node и ffmpeg
отсутствуют — нужно поставить.** ffmpeg можно не ставить системно: в проекте
уже используется npm-пакет `ffmpeg-static`, он приносит бинарник сам.

### Раскладка на сервере

```
/srv/artnazavod/
  app/                     ← собранный бандл (index.html, assets) — кладёт deploy-prod.sh
  raw/                     ← скачанное с Диска как есть
  content/
    <версия>/              ← content.json + photos/ + media/ + hero/
  current  -> content/<версия>   ← боевой
  preview  -> content/<версия>   ← предпросмотр
  state.json               ← md5 каждого файла Диска на момент последней сборки
  queue-video.json         ← видео, ожидающие ночного прогона
```

nginx: `/` отдаёт `app/`; `content.json`, `/photos/`, `/media/`, `/hero/`
— из `current`; `/preview/` — тот же `app/`, но контент из `preview`,
под basic-auth. Публикация — переключение симлинка, то есть атомарно и
без полусобранного состояния на сайте.

### Цикл (systemd-таймер, раз в 10 минут)

1. Читает публичный API Диска (`cloud-api.yandex.net/v1/disk/public/resources`)
   рекурсивно, берёт **md5 каждого файла**. Сверяет со `state.json`.
   Изменений нет — выходит молча, ничего не пишет.
2. Качает только изменившееся.
3. Фото обрабатывает сразу: sharp, `.rotate()` по EXIF, `fit:'inside'`
   ≤1600×1600, mozjpeg q80 — параметры те же, что сейчас.
4. Видео **не трогает**, складывает в `queue-video.json`.
5. Пересобирает `content.json` (тексты из манифеста + медиа из листинга),
   выкладывает новую версию в `content/<версия>` и переводит на неё
   **только `preview`**.
6. Пишет отчёт: что добавилось, что удалилось, что пропущено и почему,
   ссылка на предпросмотр.

### Ночной прогон (таймер, 03:00)

Разбирает `queue-video.json` тем же ffmpeg-конвейером (≤1920×1080, libx264
CRF 26, AAC 128k, `+faststart`, обязательный второй `scale=trunc(iw/2)*2`
— без него libx264 падает на нечётной высоте после ресайза вертикального
видео). Результат добавляется в предпросмотр, отчёт — утром.

Срочное видео — запуск того же скрипта руками с флагом, минуя таймер.

### Публикация на боевой

Отдельная команда человека (скрипт с ноутбука по ssh): переключает `current`
на ту же версию, что сейчас в `preview`. Автоматической публикации нет —
это и есть запрошенный предпросмотр. Побочный эффект: если коллега удалила
фото на Диске, удаление тоже доедет до боевого только через человека.

## 4. Отчётность

Телеграм. Отдельный чат, не канал дизайн-системы. Отчёт присылается только
когда есть что сказать: изменения, пропущенные файлы, незнакомые папки,
ошибки. Тишина = ничего не менялось.

---

## 5. Порядок работ

1. `content.json` вместо `objects.ts` + шапка из листинга + хеши в именах —
   правки в прототипе, проверяются на прод-сборке (dev-сервер не показатель).
2. `folders.json` + скрипт синхронизации с Диском (листинг, md5-диф,
   скачивание, обработка фото, сборка версии) — сначала локально, на
   настоящей папке.
3. Раскладка на сервере, nginx, basic-auth на `/preview/`, systemd-таймеры.
4. Ночной прогон видео.
5. Телеграм-отчёт.
6. Короткая инструкция коллеге: что куда класть и как называть.

Оценка: полтора-два дня. Существующие скрипты переиспользуются, с нуля
пишется только синхронизация с Диском и обвязка публикации.

---

## 6. Оговорка

Раздел в перспективе переезжает в портал sibur.ru со своей редактурой.
Поэтому полноценная CMS (Strapi/Directus) под пилот не делается: описанное
выше стоит два дня, переиспользует существующие скрипты и после переезда
просто выключается.
